SPACE TECHNOLOGIES AT CAL SIMULATION FOR AUTONOMOUS RESOURCE ROVER  
I am involved in Space Technologies at Cal, a student group building and launching multiple space projects, from high altitude balloons to microgravity experiements. I work on an autonomous resource rover, in collaboration with the NASA Ames Research Center. You can check out the project description here: https://stac.berkeley.edu/project/rover.

There are two subteams who work on the project: a mechanical team building the rover design and resource extraction, and an autonomous team building AI and supporting tools for the rover to navigate its terrain by itself. I am part of the latter team, working in simulation in developing a stable environment to test algorithms and models for autonomous decision making. Type of Work: Engineering
Team: Autonomous
Tools: ROS (Robot Operating System), Gazebo, Docker BEGINNING OF SIMULATION NEEDS In the early stages of the project, we had a Gazebo GUI running as an app on one Linux machine. While executable, it was nearly impossible to port this configuration to any other operating system (or any other machine for that matter).

Our goal for simulation was to make the setup of this environment fast and simple for anyone wishing to run our rover simulation on their machine. CONSIDERATIONS In considering our possible implementations, we ultimately narrowed down our solution with some criteria.

First, we needed a GUI, so this could not be done in a terminal. We needed to see a rover and its environment visually to understand its actions.

We considered using a virtual machine; however, they use a lot of a host's resources, and involved a lot of software and packages that would not be useful for our purpose.

We settled on using Docker, which would be able to hold all package installations needed, but would be light enough to not be a burden on the host machine. Additionally, this would make it easier to scale number of environments should we decide to parallelize the number of environments and models training at any point in time. DOCKER SOLUTION Upon running, a Docker container would install all packages and be the central environment. It would start a barebones Ubuntu environment, and a user would VNC to this Docker container's address to see the GUI.

This made setup and runtime much faster. A user would clone the docker image and start the container, with assets and local AI models in a volume mounted to the container. Then, they would open their web browser, and VNC into the container, where they would interact with the environment like they would interact with a normal GUI. NEXT STEPS For our next steps, we want to run our models in this environment, implement a non-GUI environment for training without human intervention, and parallelize containers and training to speed up the process.
